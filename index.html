배우현 · 프론트엔드 개발자

사람이 기억하던 규칙을 도구가 검증하게 만듭니다.

규칙을 문서로만 적어두면 아는 사람만 지키게 됩니다. 그래서 규칙은 지키지 않았을 때 바로 드러나는 곳에 둡니다 — 타입 시스템, CI 게이트, 자동 PR, push 훅.

React·TypeScript로 아파트 커뮤니티 플랫폼의 프론트엔드를 담당하고 있습니다. 입주민 앱부터 매장 POS·사이니지 CMS까지 6개 제품을 병행하면서, 화면을 만드는 일과 그 화면이 효율적으로 만들어지는 기반을 만드는 일을 함께 해왔습니다.

AngularJS로 시작해 Vue·Nuxt 기반 B2B 플랫폼을 거쳐 React로 주력 기술을 옮겼습니다. 직전 회사에서는 웹팀 리드로 제품 3개의 런칭을 담당하며 CI/CD와 머지 전 코드 리뷰 프로세스를 함께 세웠습니다.

일하는 방식

아래 사례는 모두 이 세 가지 중 하나에서 나왔습니다.

  • 반복되는 판단을 사람이 아니라 도구가 하게 만듭니다

    사람 손에 남아 반복되는 판단이 무엇인지 먼저 찾고, 그것을 생성·검증·갱신하는 장치로 옮깁니다. 문서를 늘리기보다, 지키지 않으면 걸리는 게이트를 두는 쪽을 택합니다.

  • 기능 하나를 끝내기보다, 다음 기능이 효율적으로 만들어지는 구조를 남깁니다

    제품마다 흩어진 설정·컴포넌트·라우팅에서 공통 축을 찾아 단일 소스로 묶습니다. 새 화면을 추가하면 권한 가드와 컨벤션이 자동으로 따라오게 만듭니다.

  • 여러 클라이언트에 걸친 도메인을 한쪽 기준으로만 맞추지 않습니다

    하나의 정책이 앱·웹뷰·POS·네이티브에 동시에 걸칠 때 상태 머신과 인터페이스 규약을 맞추고 배포 순서를 통제합니다. 제품 하나를 골격부터 운영 투입까지 단독으로 완성한 경험이 그 판단의 바탕입니다.

사례

어떤 일이 사람 손에 있었고, 지금은 무엇이 그 일을 대신하는지로 정리했습니다. 아래 일곱 건은 모두 커밋 이력으로 확인할 수 있는 작업입니다.

PR이 죽인 파일을, 그 원인이 된 줄에서 알려주게 만들기

리뷰어가 “이 파일 이제 안 쓰이는 것 같은데요”를 눈으로 찾아야 했습니다. 놓치면 죽은 코드가 그대로 쌓입니다.

이전 — 사람이 한다

  • 리뷰어가 diff를 읽다가 미사용이 된 파일을 알아채야 함
  • 놓치면 아무도 모른 채 축적. 나중에 “이거 쓰나요?” 를 다시 물음

지금 — 도구가 한다

  • CI가 이 PR로 새로 죽은 파일을 계산
  • 죽게 만든 바로 그 줄에 리뷰 코멘트가 달림

만든 것

Knip 정적 분석을 도입하고, 그 결과를 PR 리뷰 코멘트로 바꾸는 가드를 붙였습니다. 운영에서 걸린 것들을 이어서 잡았습니다 — 머지 예정 트리 기준으로 분석해 오탐 보정, 확장자 포함 상대 경로 미탐지 수정, 리뷰 배치 API 오류 대응, 무관 파일 경고를 코멘트 표로 통합.

확인 가능한 흔적 [PL-28754] feat - PR로 인해 새로 dead 파일이 된 경우 원인 줄에 리뷰 코멘트 남기기 2026-07-09, 입주민 앱 저장소. 이후 PL-28621에서 오탐을 보정하고, PL-28781로 내부 운영 콘솔에 확산했습니다. 현재 Knip이 걸려 있는 곳은 이 두 저장소입니다.

서버 스펙 변경을 런타임 장애가 아니라 컴파일 에러로 만들기

서버 응답 타입을 프론트엔드에서 손으로 다시 정의하고 있었습니다. 같은 API의 타입이 화면마다 조금씩 다르게 복사돼 있었고, 서버가 필드를 바꿔도 터지기 전까지 알 수 없었습니다.

이전 — 사람이 한다

  • 응답 타입을 화면마다 수기로 선언. 조금씩 어긋남
  • 스펙 변경을 사람이 전파. 놓치면 운영에서 터짐
  • 스키마 파일을 커밋해 팀원 간 충돌이 상시 발생

지금 — 도구가 한다

  • OpenAPI 스펙에서 타입과 쿼리 훅을 생성
  • 스펙이 바뀌면 타입 체크가 먼저 실패
  • 산출물은 Git 밖. 로컬·CI에서 그때그때 생성

만든 것

openapi-typescript → openapi-fetch → openapi-react-query로 이어지는 생성 파이프라인. 여기에 규칙을 하나 더 걸었습니다 — 파생 타입은 스키마 컴포넌트 이름이 아니라 URL 경로로만 참조한다. 서버가 스키마 이름을 바꿔도 프론트엔드 타입이 조용히 깨지지 않습니다. 환경별로 갈리던 스펙 출처는 환경 변수 하나로 묶고, 결정 배경을 ADR로 남겼습니다. 제품마다 조금씩 달랐던 생성 절차는 입주민 앱 기준으로 통일해, 저장소를 옮겨 다녀도 같은 스크립트·같은 폴더 구조가 통하게 정리했습니다.

확인 가능한 흔적 4개 제품 적용 — 입주민 앱 · 관리자 운영툴 · 내부 운영 콘솔 · 주문 키오스크 부수 효과가 하나 있었습니다. 생성된 타입이 단일 정답이 되면서, AI 에이전트가 API 타입을 추측할 여지 자체가 사라졌습니다.

문서가 낡으면, 문서가 스스로 갱신 PR을 열게 만들기

정산·쿠폰·시설 예약·인증 같은 도메인 정책은 코드에만 있어 개발자만 접근할 수 있었습니다. 사람이 쓴 문서는 코드가 바뀌는 순간부터 낡기 시작합니다.

이전 — 사람이 한다

  • 정책을 알려면 코드를 읽거나 담당자에게 물어봐야 함
  • 문서 갱신이 담당자의 성실성에 달려 있음
  • 리뷰어가 기계도 확인할 수 있는 사실까지 눈으로 재확인

지금 — 도구가 한다

  • LLM이 인덱스를 먼저 읽고 관련 페이지를 인용해 답함
  • 드리프트가 감지되면 재생성 PR이 열리고 담당자가 지정됨
  • 체크리스트가 “사실 확인”이 아니라 “해석 확인” 중심

만든 것

내부 운영 콘솔 저장소에 도메인 · 엔티티 · 기능 · 용어사전 · 플레이북 · 결정기록으로 구성된 위키 체계를 설계·정착시켰습니다. 드리프트 감지 엔진은 백엔드 유닛이 만들었고, 제가 담당한 구간은 감지된 드리프트를 받아 재생성 PR을 열고 담당자를 지정해 리뷰를 요청하는 흐름과 그 운영 품질입니다 — 리뷰 체크리스트를 해석 확인 중심으로 개정, 에이전트 실패 시 원인 진단 스텝 추가, 야간 배치 알림 카드를 일상어·커밋·담당자 정보 포함으로 개편, dispatch 방식 교체.

확인 가능한 흔적 내부 운영 콘솔 위키 — 문서 11 / 35 최초 작성 · 디렉터리 커밋 43 / 53 · 유닛 위키 저장소 23 / 371 커밋 문서 자체는 백엔드 유닛과 공동으로 축적한 것입니다. 위 숫자가 공유 저장소 기준의 제 기여 범위입니다.

제품마다 갈라진 설정을 하나로 묶고, 권한 가드를 라우팅으로 내리기

저장소마다 번들러(CRA)·린트·타입 설정이 달라 컨벤션이 파편화돼 있었습니다. 라우팅도 수동 등록이라 권한 체크가 화면마다 흩어져 있었습니다.

이전 — 사람이 한다

  • 저장소를 옮길 때마다 다른 설정·다른 규칙에 적응
  • 새 페이지를 만들면 라우트를 손으로 등록
  • 권한 체크를 화면 안에서 각자 처리. 빠뜨리면 UI만 숨겨짐

지금 — 도구가 한다

  • 공용 config 패키지를 가져다 씀. 규칙은 한 곳에서 바뀜
  • 파일을 만들면 라우트가 생김
  • AuthGuard가 라우팅 레이어에서 일괄 적용

만든 것

CRA → Vite 마이그레이션을 3개 제품(입주민 앱 · 관리자 운영툴 · 디자인 시스템)에 적용하고, Turborepo · pnpm workspace 위에 공용 config 패키지(config-typescript · config-tailwind · config-prettier · eslint-config)를 분리했습니다. 파일시스템 라우팅으로 전환하면서 useNavigate 사용 규칙과 src 직접 import 차단을 ESLint 규칙으로 강제하고, 라우터 구조는 README에 자동 생성되게 했습니다. shadcn/ui 전체는 사내 디자인 시스템 패키지로 편입해 Storybook으로 문서화했습니다.

개인 작업이 아니라 팀 전환이었기 때문에, 코드보다 기존 라우터와의 구조 비교 문서를 먼저 써서 공유했습니다. 바꾸자고 설득하는 것과 바꾸는 것은 다른 일입니다. 같은 에픽에서 계획했던 전 제품 물리적 모노레포 이관은 우선순위 조정으로 종료됐고, 현재 모노레포에 들어가 있는 것은 내부 운영 콘솔입니다.

장애를 고객 문의가 아니라 알림으로 알게 만들기

운영 중 나는 프론트엔드 오류를 CS 접수로만 인지할 수 있었습니다. 어느 단지, 어느 사용자에게서 났는지 추적이 불가능했습니다.

이전 — 사람이 한다

  • 사용자가 문의해야 장애를 앎
  • 재현 조건을 사용자에게 되물음
  • 어느 단지에서 나는 문제인지 모름

지금 — 도구가 한다

  • 모니터링 알림이 먼저 옴
  • 단지 ID · 사용자 태그가 이벤트에 붙어 있음
  • 의미 없는 오류는 걸러진 상태로 도착

만든 것

Sentry를 도입하고 릴리즈 버전 네이밍을 정리한 뒤, 에러 바운더리에서 리포팅 로직을 분리해 오류 유형별 수집 경로를 나눴습니다. 운영상 의미 없는 노이즈(홈넷 연동 오류 · 401 인증 오류)를 필터링하고 401은 핑거프린트를 분리해 별도 집계했습니다. 샘플 레이트를 조정해 비용과 신호의 균형을 잡고, 같은 체계를 사이니지 CMS에 확산했습니다.

도입 자체보다 노이즈를 걷어내는 일이 실제 작업의 대부분이었습니다. 모든 오류가 올라오는 대시보드는 아무도 안 봅니다.

하나의 번호판 인식이 앱 · 웹뷰 · 네이티브 세 지점에 걸칠 때

기존 차량번호 인식은 번호판을 지정된 인식 영역에 맞춰야만 동작했습니다. 관리자가 주차장을 돌며 여러 대를 빠르게 확인할 수 없었고, 위반 차량 통제도 신고 이력이 흩어져 수작업 판단에 의존했습니다.

이전 — 사람이 한다

  • 번호판을 인식 영역에 맞춰 한 대씩
  • 신고 화면에 차량 번호를 손으로 입력
  • 상습 위반 여부를 이력을 뒤져 판단

지금 — 도구가 한다

  • 카메라를 비추면 시야의 차량을 실시간 인식
  • 정기 · 방문 · 미등록 타입을 즉시 판별해 표시
  • 신고 화면에 번호판 자동 입력, 누적 기준으로 블랙리스트 자동 등록

만든 것

관리자 앱의 네이티브 인식 인터페이스를 운영툴 웹뷰와 연결했습니다. 신고 차량 · 블랙리스트 관리 화면(자동 등록과 관리자 수동 해제 정책, 등록 사유 · 상태 변경 주체 표기, 방문 등록 차단 안내)을 구현하고, AI 주차 리포트 진입 동선과 권한별 다운로드 분기를 붙였습니다. 모바일 웹뷰에 맞춰 차량 목록을 테이블에서 List + 무한스크롤로 바꾸고, 주차 URL 하위에서는 LNB · 헤더를 감춰 앱 내 화면처럼 보이게 처리했습니다.

어려웠던 건 인식이 아니라 경계였습니다. 네이티브가 넘겨주는 값의 규약을 정하고, 웹뷰가 앱 화면인 척하게 만드는 일이 작업의 대부분이었습니다.

현장 접속을 사람의 기억에서 앱으로 옮기기 (기획부터 릴리즈까지 단독)

현장 단지 장비에 붙으려면 bastion 서버 SSH 터널을 매번 손으로 열고 RDP를 실행해야 했습니다. 여러 현장을 동시에 지원할 때 세션과 포트를 사람이 기억하고 있어야 했습니다.

이전 — 사람이 한다

  • 터널 명령을 매번 조립. 포트 충돌은 겪고 나서 앎
  • 세션 만료 시점을 기억에 의존
  • 로그만 보면 되는 작업도 동시 접속 상한을 소모

지금 — 도구가 한다

  • 현장을 고르면 터널·포트 고정·RDP까지 자동
  • 세션 대시보드에 잔여 시간이 보임
  • 조회 전용 경로를 접속에서 분리
