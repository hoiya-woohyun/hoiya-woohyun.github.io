# 편집 원칙 — 이력서 · 경력기술서 · 포트폴리오

세 문서를 고치는 사람과 페르소나 리뷰어가 **작업 전에 반드시 읽는 파일**이다. 여기 없는
취향은 지적 근거가 되지 않는다. 원칙을 바꾸려면 이 파일을 먼저 고친다.

근거 원장: `private/정량지표-실측결과.md`(수치), `private/경력기술서-검증결과.md`(담당 범위).
원본은 `src/*.html` 뿐이고 산출물은 `make` 가 만든다. 마지막 게이트는 `make check`.

## 1. 증거 규율

1. **원장에 행이 없는 숫자는 쓰지 않는다.** 리뷰어도 새 숫자를 제안하지 않는다. 숫자를
   바꾸려면 원장 행 번호를 함께 적는다.
2. **지표에는 구간·모수·조건을 문장 안에 붙인다.** `26.4h → 2.3h` 는 `(2025.05~08)` 없이
   쓰면 다른 구간 수치로 반증된다.
3. **인과를 단정하지 않는다.** 여러 조치가 겹친 개선은 "기여도를 분리 측정하지 않았다" 가
   정답이다. "~덕분에", "~로 인해" 를 지표 앞에 붙이지 않는다.
4. **활동량은 증거가 아니다.** 커밋 수, PR 수, 티켓 수, 리뷰 건수는 늘리려면 늘릴 수 있다.
   이력서에서는 걷어내고, 경력기술서·포트폴리오에서는 결과 지표의 부연으로만 둔다.
5. **기본값 충족은 성과가 아니다.** 예정일 출시, 스토어 배포 완료, 단독 완성, 회사 프로세스
   통과는 쓰지 않는다.
6. **본인 담당이 아닌 것은 귀속하지 않는다.** 팀원의 행동, 타인이 만든 엔진, 공동 축적물은
   "함께", "이어 씀" 으로 경계를 밝힌다.
7. **약점 신호가 되는 큰 수는 쓰지 않는다.** 오류 45만 건 같은 절대량은 개선률로만 쓴다.
8. **근거 없는 정밀도를 만들지 않는다.** `1% 미만` 에서 감소율을 뽑거나, 표본 수 변화를
   개선처럼 화살표로 잇지 않는다.

## 2. 문서 경계 — 무엇을 어디에

| 문서 | 단위 | 종결 | 지표 |
|---|---|---|---|
| 이력서 | 회사 | 한자어 명사형 (`~전환`, `~확립`) | `›` 하위 항목, 한 장 안에서 한 번만 |
| 경력기술서 | 프로젝트 | 「문제」 만 서술형, 「수행」「성과」 는 명사형 | 본문 + 지표 근거 표 (반복이 설계) |
| 포트폴리오 | 제품·사례 | 서술형 `~습니다` | 산문에 녹임 |

- 경계를 넘는 내용은 옮기지 않고 **지운다**. 이력서를 다시 읽게 만드는 경력기술서 섹션이
  대표 사례다.
- **상위 항목 = 무엇을 했나, 하위 항목 = 그래서 무엇이 됐나.** 대시(`—`)에 지표나 나열을
  매달지 않는다. 대시는 한 항목에 한 번, 부연일 때만. 적용 범위는 괄호.
- `[핵심 성과]` 에는 결과, `[주요 기여]` 에는 조치. 같은 지표를 두 층에 심지 않는다.

## 3. 어휘와 문체

1. **타사 인사 담당자가 읽는다.** 현 회사 맥락이 없어도 읽혀야 한다. 사내 제품명·워크플로
   이름·티켓 번호·내부 타입명은 쓰지 않는다. 필요하면 역할로 풀어 쓴다
   (`pre_build` → `PR 사전 빌드 워크플로`).
2. **전문용어와 사내 라벨은 첫 등장에서 풀어 쓴다.** `속인화` → `담당자에게만 있던`,
   `앱 셸` → `화면 골격`. 개발자 표준어는 그대로 쓰되 비개발자 어휘(`전산망`, `코드 한 벌`)는
   개발자 표준어로 바꾼다.
3. **번역체·주니어 어미를 쓰지 않는다.** `~를 활용해` → `~로`. `~하여`, `~를 통해`,
   `~로 인한`, `~ 가능` 불채택.
4. **누구에게나 붙는 표현을 쓰지 않는다.** `프론트엔드 전문성`, `적극적인 커뮤니케이션`,
   `~에 참여`. 다른 개발자 이름을 넣어도 성립하면 지운다.
5. **부푼 이름을 붙이지 않는다.** 실체가 폰트 통일이면 `크로스 플랫폼 UI 일관성` 이라 쓰지
   않는다. 부푼 이름 하나가 진짜 큰 일의 이름까지 같은 할인율로 읽히게 한다.
6. **"리딩" 은 근거로 재구성한다.** 규격을 만들고 팀이 이어 쓰게 했으면 그렇게 쓴다.
7. **성장 서사·자기 축소를 쓰지 않는다.** "첫 경험", "범위 확장", "짧은 기간이라" 는 지운다.
   실제 6개 이상인데 6개로 줄여 쓰지 않는다.
8. **반복 문형은 세어서 깬다.** "A를 B로 전환/이관" 이 한 문서에 열 번 넘으면 재작성한다.
9. **AI 티 판정은 빈도로 한다.** `확립 3회` 는 정상, `담당 26회 · 기반 27회` 가 과다다.
10. **표기 통일**: `론칭`(`런칭` 아님), `주식회사 에이치티비욘드`(영문·`(주)` 아님, 다른 회사와 같은 형식),
    경력은 `7년 6개월` 한 축(`N년차` 병기 안 함). 새 항목은 `make check` 의 `VARIANTS` 에 더한다.
11. **빈 섹션은 만들지 않는다.** 대외활동·자격증·교육에 채울 것이 없으면 섹션째 없앤다.

## 4. 페르소나 리뷰 절차

**로스터 (고정, 3명)**

| 페르소나 | 심사 영역 | 보지 않는 것 |
|---|---|---|
| 타사 인사 담당자 | 현 회사 맥락 없이 읽히는가 · 비개발자 이해도 · 종결·서식 통일 · 첫 20줄의 인상 | 기술 판단 |
| 현직 FE 동료 | 지표가 원장과 맞는가 · 과장 · 문제→수행→성과 논리 · 기술 서술의 정확성 | 문체 취향 |
| 채용하는 팀장 | 리소스 대비 산출 · 포장 냄새 · 뽑을 이유가 문장에 있는가 · 리드 경험의 실체 | 서식 |

**한 라운드**

1. `make md` 산출물(`private/현재본-md/*.md`)을 세 페르소나가 **블라인드 병렬**로 읽는다.
   서로의 결과를 보지 않는다. 각자 이 파일과 원장을 먼저 읽는다.
2. 지적은 아래 형식으로 낸다. 형식을 벗어난 지적은 버린다.
   ```
   | # | 등급 | 위치(섹션·인용 10자 이내) | 문제 | 제안 문장 | 근거(원칙 번호 또는 원장 행) |
   ```
   등급: **P1** 사실 오류·원장 불일치·귀속 오류·사내 정보 노출 / **P2** 원칙 위반
   (문체·경계·어휘) / **P3** 취향.
3. **합의 판정**
   - P1 은 **한 명만 짚어도 반영**한다. 단 사실 여부는 원장으로 재확인한다.
   - P2 는 **두 명 이상**이 같은 줄을 짚으면 반영, 한 명이면 사용자 결정 큐.
   - 예외: **한 페르소나만 맡은 심사 영역**(문체·서식·어휘 = 인사, 포장·부푼 이름 = 팀장,
     지표·시점 표기 = FE)의 P2 는 원칙 번호를 댔으면 혼자 짚어도 반영한다. 그 영역은
     구조적으로 2명 합의가 나올 수 없기 때문이다. 단 블록 삭제·결론 재배치 같은
     **구성·분량 변경은 예외 대상이 아니다** — 항상 사용자 결정 큐.
   - P3 는 반영하지 않고 기록만 한다.
   - 사실 충돌은 투표하지 않고 **재측정**한다. 취향 충돌은 사용자에게 넘긴다.
4. **토론은 충돌 항목에만** 연다. 블라인드 결과가 나오기 전에 토론시키지 않는다.
5. 편집자는 `src/*.html` 만 고친다. 새 숫자 금지. 한 문서를 고치면 같은 사실이 있는
   **다른 두 문서를 같이 고친다**.
6. `make && make check` 통과 후 커밋. 보고서는 `| 전 | 후 | 왜 |` 표, 미반영 지적 전부의
   사유 표, "본인만 결정할 수 있는 것" 목록으로 끝난다.

**종료 조건**: P1 0건이고 P2 합의가 2건 이하이면 그 문서는 끝. 최대 3라운드. 이후 지적은
취향 핑퐁이므로 돌리지 않는다.

**순서**: 경력기술서 → 포트폴리오 → 이력서.
