AI가 읽는 정책 문서와 OpenAPI 타입 생성

핵심 업무 2024.02 ~ 2026.11
문제

도메인 정책을 개발자, PO, 디자이너 별로 별도 관리하여, 8개 제품에 걸친 기획이 바뀌면 어느 문서가 최신인지 판별하기 어려웠고, 문서끼리 맞추는 동기화 작업에 비용이 들었습니다. Claude Code도 기획을 알 수 없어 소스 전체를 훑어야 하는 경우가 많았습니다. 응답 타입도 제품마다 손으로 선언해, 서버가 스펙을 바꾸면 배포 후 운영에서야 드러났습니다.

판단
  • 파생 타입의 기준을 스키마 컴포넌트 이름 대신 URL 경로로 정함
    • 스키마 이름은 서버가 바꿀 수 있지만 경로는 API 계약이라 덜 흔들림
  • 생성 산출물을 커밋하는 대신 로컬·CI에서 빌드 시점에 생성
    • 여러 브랜치가 같은 스키마 파일을 잇달아 갱신하며 생기던 머지 충돌 제거
수행
  • 저장소 문서를 구조 설계·결정 기록(ADR)·기능 명세·화면 스펙·버그 원인 분석 5종과 색인으로 나누고, 코드를 고치면 갱신할 문서를 AGENTS.md·CLAUDE.md 규칙으로 강제
  • openapi-typescript로 OpenAPI 스펙에서 타입·클라이언트·쿼리 훅을 생성하는 파이프라인을 4개 제품에 도입
  • 흩어진 도메인 정책을 출처를 인용하는 LLM 위키로 정리 (백엔드 팀과 공동)
  • 정기 배포 후 Claude가 변경 코드를 읽어 위키와 어긋난 내용을 찾으면 문서 수정 PR을 열어 담당자에게 리뷰를 요청하는 GitHub Actions 구현 (위키 구조는 백엔드 팀)
성과
  • 버그 원인 분석 문서 형식을 정해 팀 공통 양식으로 정착, 현재까지 지속 관리 중
    • 버그 분석 문서 102건 중 본인 59건, 나머지 40건은 팀원 4명이 같은 형식으로 작성
  • API 타입을 직접 정의하던 방식에서 생성된 타입을 참조하는 방식으로 전환
    • API 1건을 연동할 때 직접 작성하던 코드를 평균 35줄에서 4줄로 축소 (이전 방식 POS 정의 52건 기준 구조 값)
  • 서버 스펙 변경을 배포 전 타입 생성 단계의 컴파일 에러로 확인
  • 도메인 정책 확인 창구를 담당자 문의에서 위키 한 곳으로 일원화
    • 담당자 기억에 기대던 문서 동기화를 배포마다 오는 수정 PR 리뷰로 대체
스택

OpenAPI(openapi-typescript · openapi-fetch · openapi-react-query) · Claude Code · GitHub Actions · MCP · AGENTS.md / CLAUDE.md 규칙 · ADR · Figma Code Connect

입주민 모바일 웹앱 — 멀티 브랜드 구조 설계와 차세대 버전

2024.04 ~ 2026.11
제품

아파트·오피스텔 입주민용 모바일 웹뷰(iOS·Android 네이티브 앱 탑재). 공지·시설 예약·주차·방문차량 등 단지 생활 기능을 담당하는 주력 제품 · DAU 약 5만 · MAU 약 35만

문제

건설사·브랜드마다 요구하는 화면과 제공 기능이 달라, 계약 버전마다 고정 브랜치를 만들어 따로 배포했고 권한 체계는 계약사별로 다른 기능 구성을 표현하지 못했습니다.

판단
  • 브랜드마다 코드베이스를 나누는 대신, 브랜드마다 실제로 다른 것은 보이는 레이아웃이고 단지 생활 기능은 같다고 보고 분기 지점을 레이아웃 한 층으로 좁힘
  • 계약사마다 다른 기능 구성은 코드 분기가 아니라 권한(구독 기능 묶음)으로 표현
수행
  • 서브도메인으로 단지를 식별하고 브랜드별 레이아웃만 분기하는 구조를 설계해, 단일 코드베이스로 브랜드별 웹뷰를 동시 서비스
  • 계약사·단지·사용자 3계층 권한을 계약사가 구독하는 기능 묶음 단위로 재설계
  • 메뉴 관리를 새로 만든 사내 운영 콘솔로 이관
  • 스마트홈(홈넷) 연동의 OAuth 콜백 구조를 재설계해 운영 환경에서만 되던 연동을 개발·알파 환경에서도 동작하도록 전환, 계정 ID 길이 제약으로 연동하지 못하던 사용자 문제 해소
  • iOS·Android 네이티브 웹뷰 호환성 대응
    • iOS 웹뷰에서만 뒤로가기 스택이 틀어지던 문제 — 이탈 방지 모달이 history 를 두 번 조작하던 것을 바로잡고, 스와이프백과 앱 내 뒤로가기를 구분해 화면 전환을 분기
    • Android 물리 백버튼은 가장 나중에 연 바텀시트·모달부터 닫도록 오버레이 스택 구현 · 구형 앱의 safe-area 이중 여백은 앱 버전 기준으로 보정
    • iOS 웹뷰에서 동적 import 가 실패하면 화면 전체가 멈추던 문제 — 백오프 재시도·조건부 1회 새로고침과 라우트 청크 재시도 Vite 플러그인으로 자동 복구
    • 저사양 Android 웹뷰에서 프레임이 떨어지던 애니메이션을 transform·opacity 기반 CSS 로 바꿈 · 바텀시트 높이 100dvh 적용 · 백그라운드 상태의 View Transition 오류 차단
    • 카카오톡 인앱·WebKit 팝업에서 window.opener·localStorage 가 null 이라 나던 오류 방어
성과
  • 건설사 브랜드 7종을 코드베이스 1개로 서비스
    • 브랜드가 늘어도 코드베이스가 갈라지지 않음
  • 계약사별 기능 구성 변경을 브랜드별 코드 분기 없이 권한 설정과 1회 배포로 반영
스택

사내 운영 콘솔

2024.02 ~ 2026.11
제품

본사 운영팀용 사내 운영 콘솔(모노레포). 단지 개설 초기 설정, 출입카드·세대·시설·현장 기기 등록과 단지 현장 서버 동기화

문제

단지 운영에 필요한 설정이 화면마다 흩어져 있어, 단지를 열 때마다 개발자가 단지·날짜·언어 단위로 대신 등록했습니다. 누락되면 오픈 후에야 드러났습니다.

수행
  • 단지 개설 초기 설정을 콘솔 한 화면의 일괄 설정으로 통합
  • 엑셀을 붙여넣어 일괄 등록·검증하는 표 컴포넌트 구현
    • 엑셀과 복사·붙여넣기가 서로 오가고, 행 추가 버튼 없이 엑셀처럼 끝에서 행이 이어지는 자체 데이터 그리드 엔진으로 교체
  • 콘솔 설정을 단지 현장 서버로 내려보낼 때 비밀번호 재확인·버전 미달 시 동기화 차단 등 현장 반영 안전장치 설계
  • 시설 상세에서 기기를 연결(매핑)하는 화면을 만들고, 연결을 끊을 때 딸린 컨트롤러·하위 기기까지 함께 해제될 행을 판정해 확인 모달로 알린 뒤 반영
    • 바뀐 행만 보내도록 해 서버가 기존 시설 연결을 지우는 일을 막음
    • 외부 연동(마이힐스/마이디에이치)용 단지·시설·기기 일괄 매핑 관리 기능
  • 단지 → 시설 → 기기 연결을 한 화면에서 보는 시설 관계도를 React Flow 로 PoC 부터 만들어 Beta 출시
    • 단지 이동·검색·필터·줌 제한 제공, 노드 1,000개 규모에서 입력할 때마다 재배치하지 않게 개선
  • 엘리베이터 동·라인·호기 매핑과 CAR ID 자동 채번 표, 세대 엘리베이터 호출·운행 모니터링 화면 개발 — 실험실 기능을 기기 관리 정식 메뉴로 이관
  • 골프타석 운영 정책 화면 — 타석별 발권 금액, 그룹별 요금, 요금과 분리한 할인 설정, 연동 시스템 추가
  • 독서실·사우나 정책을 목업에서 실제 API 로 연동하고, 시설 상세에 예약 대상 탭 추가
  • 현장 설정 「연동」 탭에 주차 관제 벤더(세진시스코·아이원코리아)·홈넷 단지 설정·엘리베이터 바로가기 추가
  • 권한을 한 표에서 조회·수정하는 권한 매트릭스 페이지 개발
  • 예약상품 키오스크 설정을 기존 사내 관리 시스템에서 콘솔로 이관, NFC 태그 관리를 기기 관리 메뉴로 옮기고 현장별 현황 목록과 편집 그리드로 개편
  • 실험실(검증용 메뉴)에 방문차량 관리·홈넷 송신 로그·마이힐스 테스트 예약 화면 개발
성과
  • 단지 개설 초기 설정 주체를 개발자에서 기술영업팀으로 이전
    • 출입카드·세대·시설·예약 대상·현장 기기 등록에 개발자가 들어가지 않음
    • 설정 누락이 오픈 후가 아니라 등록 단계의 화면·서버 이중 검증에서 드러남
스택

React · TypeScript · Turborepo · pnpm workspace · React Router · TanStack Query · TanStack Table · TanStack Virtual · React Flow · Tailwind CSS · AWS S3

관리사무소 운영툴

2024.01 ~ 2026.11
제품

단지 관리사무소가 쓰는 운영툴. 입주민·세대 관리, 커뮤니티시설·식당 예약 운영, 주차·방문차량 관리(관리자 앱 웹뷰 포함)

문제

식당 예약 상품은 운영하는 날짜마다 상품을 새로 등록해야 했습니다. 화면은 PC 전제라 주차장 현장에서 쓰기 어려웠고, 고객사 개인정보 점검에도 대응해야 했습니다.

수행
  • 매장 기본 운영 정책을 먼저 정의하고 개별 날짜·시간대는 예외만 덮어쓰는 구조로 식당 예약 상품 관리 재설계
  • 베트남 샘플하우스 오픈에 맞춰 운영툴에 i18next 를 들여 한국어·영어·베트남어 화면 지원 — 입주민 앱의 번역 생성기를 옮겨 오며 시트 리더·검증 스크립트는 새로 작성 (번역 문구는 고객 측 제공)
    • 번역 시트 헤더가 밀리면 고유 키 4,824개가 28개로 덮어써지던 문제를 반영 전 검증 실패로 차단
  • 고객사 개인정보 점검에 맞춰 입주민 관리 화면의 이름·동호수·연락처·카드 ID를 기본으로 가리고 필요할 때만 여는 마스킹을 화면에 적용 (마스킹·열람 기록 서버는 백엔드 팀)
    • 승인·반려처럼 원본 값이 필요한 동작은 가려진 값이 서버로 가지 않게 요청을 분리
  • PC 화면 전제였던 단지 주차 관리를 관리자 앱 웹뷰에서 주차장을 돌며 쓰는 화면으로 전환 — 메뉴 없는 전용 경로, 모바일 목록·무한 스크롤, 신고 화면 바로 진입
  • 입출차 현황에서 방문증 없이 들어온 차량을 골라 그 자리에서 방문증을 만들어 연결하고, 기한 없이 쓰는 방문 차량 등록·신고 차량 관리 화면 개발
  • 정기 이용권 운영 정책 설정 화면 개발 — 앱 취소 정책, 익월 사용 옵션, 세대 인증 해제 시 사용 중인 이용권 안내
  • 사내 운영 콘솔에서 먼저 만든 엘리베이터 호출·운행 모니터를 운영툴로 이식하고, 월간 운영 리포트 PDF 다운로드·세탁기 점검 중 수동 설정·골프타석 대기 사용 설정 화면 개발
성과
  • 식당 예약 상품을 운영 날짜가 늘어도 등록 작업이 함께 늘지 않는 구조로 전환
스택

React · TypeScript · React Router · TanStack Query · Ant Design · styled-components · i18next · SheetJS

BYB-CMS 신규 구축

프론트엔드 단독 2025.01 ~ 2025.11
제품

단지 내 디스플레이 기기에 광고·공지를 송출하는 관리 시스템. 매체·소재·캠페인 등록부터 송출 편성, 설치 기기 원격 관리까지

문제

신규 제품이라 프론트엔드에 선례가 없었고, 광고 운영·기기 관리·정산이 한 콘솔에 들어와야 했습니다. 인력은 프론트엔드 1명이었습니다.

수행
