API 타입 자동 생성 파이프라인

기간
2025.06 – 2026.08
범위
4개 제품
역할
설계 · 구축 · 확산
문제

서버 응답 타입을 프론트엔드에서 수기로 다시 정의하고 있었습니다. 서버가 필드를 바꿔도 프론트엔드는 런타임에 터지기 전까지 알 수 없었고, 같은 API의 타입이 화면마다 조금씩 다르게 복사돼 있었습니다.

수행

  • OpenAPI 스펙에서 타입과 쿼리 훅을 생성하는 파이프라인 구축

    openapi-typescript · openapi-fetch · openapi-react-query 조합. 화면마다 조금씩 다르게 복사돼 있던 수기 타입 정의를 전부 없앴습니다.

  • 파생 타입을 URL 경로 기준으로만 참조하도록 컨벤션 정립

    서버가 스키마 컴포넌트 이름을 바꿔도 프론트엔드 타입이 조용히 깨지지 않습니다. 규칙 파일로 문서화해 사람과 AI가 같은 방식을 쓰도록 했습니다.

  • 생성 산출물을 Git에서 분리하고, 제품별로 다르던 절차를 통일

    로컬·CI에서 그때그때 생성합니다. 환경(dev·alpha·운영)별로 갈리던 스키마 출처는 환경 변수 하나로 묶고 결정 배경을 ADR로 남겼습니다. 4개 제품이 같은 스크립트·같은 폴더 구조를 씁니다.

결과

서버 스펙 변경이 런타임 장애가 아니라 컴파일 에러로 드러나게 되었고, 팀원 간 스키마 파일 충돌이 구조적으로 사라졌습니다. 부수적으로 AI 에이전트가 API 타입을 추측할 여지 자체가 제거됐습니다.

AI가 읽을 수 있는 코드베이스 만들기

기간
2026.04 – 2026.08
기여
ADR 31/34 · 규칙 18/21
문제

AI 도구를 도입해도, 프로젝트의 암묵적 컨벤션(라우팅 규칙·네이밍·디자인 시스템 사용법·금지 패턴)이 사람 머릿속에만 있으면 AI는 매번 틀린 코드를 냅니다. 리뷰 비용이 오히려 늘어납니다.

수행

  • 저장소 문서 체계 설계 — docs/ 다섯 축과 갱신 강제 규칙

    architecture(구조 설계) · decisions(ADR) · features(기능 명세) · specs(화면·컴포넌트 스펙) · bugs(원인 분석)로 나누고, 각 폴더의 역할과 작성 원칙을 docs/README.md에 규정했습니다. 여기에 관련 코드를 수정하면 해당 문서도 함께 갱신해야 한다는 조항을 에이전트 규칙에 넣어, 문서 갱신을 사람의 성실성이 아니라 작업 절차의 일부로 만들었습니다. 지금은 결정 기록 34건 · 버그 분석 97건이 같은 규격으로 쌓여 있고, 에이전트가 새 작업을 시작할 때 먼저 읽는 층입니다.

  • 저장소별 에이전트 규칙 파일 체계 구축 — 21개 규칙 중 18개 직접 작성

    AGENTS.md · CLAUDE.md · Cursor Rules. 라우팅 규약, 절대 경로 import, 타입·인터페이스 네이밍, 디자인 시스템·OpenAPI 클라이언트 사용 규칙 등. 규칙이 늘수록 컨텍스트 비용이 커지므로 실제로 위반이 잦은 항목만 남기고 경량화했습니다.

  • 아키텍처 결정 기록(ADR) 체계 도입 및 운영 — 34건 중 31건 직접 작성

    세션 저장소 단일 출처, 라우트 통합, 스키마 환경 분리 등. “왜 이렇게 되어 있는가”를 사람과 AI가 함께 읽을 수 있는 형태로 축적했습니다.

  • Figma MCP 연동 및 Code Connect 매핑

    디자인에서 코드를 생성할 때 사내 디자인 시스템 컴포넌트를 쓰도록 유도합니다.

  • 사내 코드베이스와 별개로 — 내 작업 환경의 티켓 흐름과 권한 경계

    팀에 강요하지 않고 제 환경에서 먼저 검증하고 있는 것입니다. Jira 티켓과 상위 이슈의 설명까지 읽어 무엇을 만들려는 작업인지 복원한 뒤 격리된 worktree에서 착수하고, 커밋까지는 승인 없이 진행하되 브랜치 최초 push는 셀프 코드리뷰를 통과해야 나갑니다. 에이전트에게 어디까지 맡기고 어디서 사람을 끼울지를 규율이 아니라 실행 경로로 정한 것입니다.

결과

해당 저장소의 에이전트 규칙·설계 문서 커밋 393건 중 277건(약 70%)을 작성 — 코드베이스의 “기계가 읽는 지식 계층”을 사실상 단독으로 운영했습니다.

도메인 지식의 LLM Wiki화 · 문서 자동 재생성

기간
2026.06 – 2026.08
역할
백엔드 유닛과 공동 진행
문제

도메인 정책(정산·쿠폰·시설 예약·인증)은 코드에만 있어 개발자만 접근할 수 있었고, 사람이 쓴 문서는 코드가 바뀌는 순간부터 낡기 시작했습니다.

수행

  • 소스 코드를 원천으로 도메인 지식을 인용 가능한 위키로 구조화

    도메인 · 엔티티 · 기능 · 용어사전 · 플레이북 · 결정기록 체계를 설계했습니다. LLM이 인덱스를 먼저 읽고 관련 페이지를 찾아 인용과 함께 답하는 형태입니다. 35개 문서 중 11개 최초 작성(해당 디렉터리 커밋 43/53건). 위키를 질의 가능한 지식 소스로 노출하는 로컬 MCP 서버와, Confluence·Jira·Figma 기획서를 마크다운으로 추출하는 수집 계층은 개인 작업 디렉터리에서 선행 프로토타입으로 제작했습니다.

  • 감지된 드리프트를 받아 재생성 PR을 여는 구간 구현 — 담당자 지정 · 리뷰 요청까지

    드리프트 감지 엔진은 백엔드 유닛이 먼저 구축했고, 감지 결과를 받아 재생성 PR을 열고 담당자를 지정해 리뷰를 요청하는 구간을 붙였습니다. 이후 에이전트 실패 시 원인 진단 스텝 추가, dispatch를 gh CLI에서 REST로 교체(러너에 gh 없음) 등 운영 안정화와 인증 토큰 이관을 담당했습니다(저장소 전체 371 커밋 중 23건).

  • 재생성 PR 체크리스트를 “사실 확인”에서 “해석 확인” 중심으로 규약 개정

    한 PR에서 7개 항목 중 3개가 “응답 필드명이 X 맞나요?” 같은 사실 확인이었습니다 — 아니라고 답해도 틀리는 건 위키가 아니라 에이전트의 코드 독해라, 코드·lint 가 정본인 값을 사람에게 묻고 있었습니다. “리뷰어가 아니오라고 답하면 위키의 무엇이 틀리는가”를 말할 수 없으면 항목이 아니다라는 자격 시험을 도입해 사실 확인 항목을 배제하고, 코드가 무엇으로 바뀌었는지가 아니라 그 변화를 무슨 의도로 읽어 문서를 어느 방향으로 서술했는지를 묻게 했습니다. 근거 제시 의무는 유지했습니다 — 완화했을 때 병렬 에이전트가 항목을 지어내는 실패를 이미 겪었기 때문입니다.

결과

도메인 지식이 “물어봐야 아는 것”에서 “AI에게 질문하면 근거와 함께 답이 나오는 것”으로 전환됐고, 문서 갱신이 사람의 성실성이 아니라 파이프라인의 기능이 됐습니다.

코드 품질 자동 검증 — 사람이 지적하던 것을 CI가 지적하게

기간
2026.06 – 2026.08
역할
가드 직접 구현 · 운영
수행

  • 미사용 파일 가드 직접 구현 — PR로 새로 죽은 파일이 생기면 그 원인이 된 줄에 리뷰 코멘트를 남긴다

    입주민 앱에 Knip 정적 분석을 도입한 뒤 내부 운영 콘솔로 확산했습니다. 머지 예정 트리 기준 오탐 보정, 확장자 포함 상대 경로 미탐지 수정, 리뷰 배치 API 오류 대응까지 운영 안정화를 담당했습니다.

  • 타입 검증 파이프라인이 개발 흐름을 막지 않도록 재배치

    feature 브랜치에서는 타입 체크를 완화하고 CI 타입 검증은 리포팅 전용으로 전환. 자동 라벨링 워크플로는 이벤트 유실 시 다음 push에서 백필하도록 자가치유를 보강했습니다.

  • 조직 공통 AI 코드리뷰 GitHub Actions 도입 참여

    각 저장소가 복사해 쓰던 워크플로를 재사용 워크플로 한 벌로 통합했습니다. 실제 앱 화면 스냅샷 자동 촬영 파이프라인은 수집 대상 경로 인벤토리까지 완료했고 Playwright 수집기는 진행 중입니다.

결과

지적의 주체가 리뷰어에서 CI로 이동했습니다. 무엇을 머지 차단으로 두고 무엇을 비차단 리포트로 둘지는, 검증이 개발 흐름을 막지 않도록 갈랐습니다.

수행

기간

범위

문제

기존 차량번호 인식은 번호판을 지정된 인식 영역에 맞춰야만 동작해, 관리자가 주차장을 돌며 다수 차량을 빠르게 확인하기 어려웠습니다. 위반 차량 통제도 신고 이력이 흩어져 있어 수작업 판단에 의존했습니다.

수행

  • 관리자 앱의 네이티브 번호판 인식 인터페이스를 운영툴 웹뷰와 연결

    카메라를 비추면 시야에 들어온 차량 번호를 실시간으로 인식하고, 정기 · 방문 · 미등록 차량 타입을 즉시 판별해 표시합니다. 주차 신고 화면에 진입하면 인식된 번호판이 자동으로 채워집니다.

  • 신고 차량 · 블랙리스트 관리 체계 구현

    신고 누적 기준에 따른 자동 등록과 관리자 수동 해제 정책, 등록 사유·상태 변경 주체 표기, 필터·뱃지, 방문 등록 차단 안내를 담당했습니다.

  • 모바일 웹뷰 최적화

    차량 목록을 테이블에서 모바일 List + 무한스크롤로 전환하고, 신고 Drawer를 모바일 대응·자동 오픈하도록 했습니다. 주차 URL 하위에서는 LNB·헤더를 감춰 앱 내 화면처럼 보이게 처리했습니다. AI 주차 리포트는 입주민 앱 홈에서 바로 진입하는 동선을 추가하고 다운로드는 권한에 따라 노출을 분기했습니다.

특징

하나의 도메인이 관리자 앱(네이티브) ↔ 운영툴(웹뷰) ↔ 입주민 앱 세 지점에 걸쳐 있어, 네이티브 인터페이스 규약을 맞추고 웹·네이티브 경계에서의 화면 전환을 설계하는 일이 작업의 핵심이었습니다.
